This is the accumulated, evidence-based record of every significant bug class, architectural fix, and investigation conducted on this codebase. For confirmed **Kylas application** bugs specifically, see `APPLICATION_BUGS.md` — this file covers everything else: code bugs found and fixed, architectural overhauls, and flakes investigated but not conclusively resolved. **Consolidated 2026-09-07** — fully-resolved investigations were compressed to their durable lesson/fix; genuinely open items and standing patterns kept in full. ### Session-expiry recovery — architecture (resolved)

`BasePage.withSessionExpiryRecovery<T>()` is the final result of 5 independent fix attempts that each recurred (2026-07-09 through 07-20) before a full-codebase grep found 80 further raw `expect(...).toBeVisible/toHaveText/toHaveURL` calls across Contacts/Companies/Deals/Leads/CallLogs/Tasks/Quotations, all silently unprotected. Verified facts: no cookie-based session — clearing `localStorage` alone immediately redirects to `/signIn`; login is `PUT {apiBaseUrl}/users/login`, JWT in `localStorage.token`, every API call sends `Authorization: Bearer <accessToken>`. A `page.route()`-based interceptor design was built and verified to partially work, then deliberately abandoned: `route.fetch()` itself — even on requests nowhere near a 401 — broke unrelated saves with generic `HTTP 400`s (A/B tested decisively). **`route.fetch()`-based interception is confirmed unusable for this app — do not re-attempt.**

Final architecture: one shared combinator (`withSessionExpiryRecovery`) replaced all 80 raw call sites; `authManager.isSessionExpiryPage()` recognizes both a `/signIn` redirect AND a distinct, URL-unchanged "Forbidden" bootstrap-time page (confirmed no test relies on "Forbidden" as an expected RBAC-denial outcome, so recognizing it as expiry can't mask a real assertion); `AuthManager.ensureFreshSession()` proactively refreshes via headless login when <10 min remain on the JWT's own embedded expiry, wired into `fixtures/index.ts`. `withSessionExpiryRetry(workflowFn)` wraps a whole workflow method and retries it once on detected expiry — deliberately **not** applied to share/reassign/clone/add-from-panel methods (confirmed these assume the page is already on a specific entity's detail view; a blind retry after recovery navigation would fail worse).

`config.buildApiUrl(path)` is the **only** canonical URL-normalization function, born from two separate confirmed bugs: `loginHeadless()`'s hardcoded `/v1`-included assumption broke against CI's differently-shaped `apiBaseUrl` secret (`HTTP 404` on ~64-98 failures per run until fixed), and — found the very next day, in a call site the first fix's own ripple-check had already grepped and dismissed as "logging only" without reading what it did — `DealsPage.fetchCurrentDealApiData()` had an independent copy of the identical mistake, silently swallowed with zero logging on either branch. **Do not hand-roll a third copy; consolidate into `buildApiUrl()`.**

### ID-capture and response-matching (resolved)

`captureXxxIdFromResponse()`-style predicates must require the real versioned `/v1/<module>/` path and exclude `/reports/` — a bare `.includes('/deals')`/`.includes('companies')`-style substring match was confirmed to false-positive against an unrelated background analytics POST (`/v4/reports/deals`) in 3 places (Deals, Companies, a Deals-quotation flow), silently capturing `null` and throwing a false "save failed silently" error despite a genuine success toast. All 3 fixed. **Any new `captureXxxIdFromResponse()` must require the versioned path from the start.**

Session-expiry recovery for `waitForResponse()` ID-capture had two further races, both found via deliberate reproduction and fixed: a flag-based coordination race in `armResponseWaitWithRecovery` where code reacting to the same failure faster than the 10+s recovery (e.g. `assertNoFormErrors()`, ~1.5s) could throw before the flag was ever set — fixed via a synchronous `hasFired()` signal; and a competing-navigation race in `tryRecoverSessionForPage()` where the app's own frontend independently redirects to `/signIn` on the same 401 (`net::ERR_ABORTED`) — fixed with a bounded retry keyed on that exact signature.

### Navigation-drift gap across 6 modules (resolved, 2026-07-27)

Every `waitForXDetailsPage()`/`waitForListReady()` across Deals/Companies/Contacts/Leads/Tasks/Quotations shared the same gap: `waitForUrl()` resolves the first moment a URL matches with no guarantee it stays matching, and the follow-up entity-GET wait was wrapped in a silent `.catch(() => null)` — under real concurrent load the app's client-side router could bounce away before the GET fired, surfacing much later as a generic element-not-found timeout with zero diagnostic signal. Confirmed identical shape in Companies/Contacts/Leads (list+detail) and Tasks/Quotations (detail); Meetings/Call Logs confirmed clean. **Fixed** with two shared `BasePage` methods, `waitForEntityDetailPage()`/`waitForEntityListPage()`, replacing 6 independently-drifting copies — worst case ~190s (down from unbounded 480s), realistic time-to-clear-failure ~35-40s.

Same investigation found and fixed two further bugs: `DealsPage.getAssociatedContactId/Name()`/`getAssociatedCompanyName()` had no explicit timeout at all (this codebase never sets `actionTimeout`, whose real Playwright default is 0/unbounded) — fixed with an explicit 10s bound; and a zombie session-expiry listener left alive by `Promise.race`'s abandoned losing branch in `waitForEntityListPage()`/`TasksPage.waitForListReady()` — could keep listening up to 60s after the calling method returned (confirmed via a real full-suite run: two unrelated recovery attempts fired within 3ms of each other for calls that had returned 27-54s earlier) — fixed by swapping the race's response branch to a plain, listener-free `page.waitForResponse()`.

### Random-option-pick dropdown hangs (resolved)

6 call sites across `DealsPage.ts` (product row, associated contact), `TasksPage.ts`, `CallLogsPage.ts`, `MeetingsPage.ts` picked a random react-select option via an unbounded `textContent()`+`.click()` shape; also found that retrying the *same* index is sometimes futile (one index can be persistently non-actionable while others work fine). **Fixed** via one shared `BasePage.selectRandomOptionWithRetry(options, description, opts?)` — 3 attempts, each bounded to 15000ms, each re-rolling a fresh random index. **Use this for any new "pick a random option from an open react-select menu" call site.**

`DealsPage.fillDealForm()`'s associated contact/company pick is random **by design** (a deliberate 2026-07-05 CI-hang fix, not a bug) — pass `associatedContactName`/`associatedCompanyName` on `DealData` whenever ownership matters for a new Deals test. `BasePage.fillSearchAndWaitForOptions()`'s transient-network retry allowlist (`TRANSIENT_NETWORK_ERROR_PATTERNS`) is deliberately narrow (DNS/connection reset/refused/timeout/unreachable only, explicitly excluding real HTTP 4xx/5xx and routine `ERR_ABORTED`) — **do not widen without the same live-evidence bar.**

### Credential leakage into plaintext logs (resolved, 2026-07-20)

### Reports module — confirmed findings

Two confirmed real application bugs from this work (`removeDimension()` client-side `TypeError`, a non-functional "Report Name" sort control) are in `APPLICATION_BUGS.md` #2/#3, not here.

- **A third-party-widget-triggered react-select race is repo-wide, not Reports-specific — fixed, pattern documented for reuse.** The `viasocket.com` chatbot widget on every page can fire an async DOM mutation 20-160ms after a react-select menu opens, closing it before an automated click lands. Two approaches were tried and ruled out: blocking the widget's domain via `page.route().abort()` hung the whole browser session 30 minutes (retried aggressively); waiting for the widget's own network response first was insufficient (the disruptive re-render lands 130-160ms *after* the response). **Proven fix** — open, wait visible, then confirm the menu **survives a stability window** before trusting it (a `waitFor({state:'hidden'})` timeout is the success case) — documented in `.claude/reference-patterns.md` §18, verified via 45 combined trials with zero failures. Check for this race before assuming a module-specific bug on any "menu closed before I could click" symptom.
- **`getDestinationListTotalCount()`-style reads should default to `span.update`, not `#totalRecords`** — confirmed universal across Lead/Deal/Contact/Company/Task/Meeting/Quotation/Call Log; `#totalRecords` isn't reliably present.

### CI reporting-history ledger — root cause confirmed, fixed and merged to dev (2026-08-24/25)

`ci/reporting-history` (feeding Module Analytics' trend column and recurring-flaky/regression detection) had never received data in any real CI run, ever — masked by its own "never fail the build" try/catch. **Real root cause (found only on a third investigation round, after two rounds chased a false signal):** `syncHistory.ts` clones into its own fresh temp directory to do git work, and `actions/checkout@v5`'s `token: secrets.PIPELINE_TOKEN` only authenticates the *original* checked-out workspace — never passed through to the temp clone. ### Sharding order-dependency audit (2026-09-09) — no genuine risk found, but one non-obvious mechanism worth knowing before adding an order-dependent test

Investigated on explicit request, before trusting sharding further: does any test in this suite depend on another having run first, and does Playwright's sharding actually protect against that? Read the installed Playwright package's own sharding source (`node_modules/playwright/lib/runner/index.js`'s `createTestGroups()`/`filterForShard()`) directly rather than assuming documented behavior. Report-only investigation; no code changed as part of this entry.

**Non-obvious, durable finding: with `fullyParallel: true` (set globally in `playwright.config.ts:8`), Playwright does NOT guarantee tests from the same spec file land in the same shard — `test.describe.configure({ mode: 'serial' })` is the ONLY mechanism that keeps a block of tests atomic under sharding.** Confirmed at the source: `fullyParallel: true` sets the top-level project suite's `_parallelMode = "parallel"` (`runner/index.js:2496`), which every test inherits unless a closer ancestor overrides it. A file/describe block with no explicit mode override and no `beforeAll`/`afterAll` has each of its tests become its own **independent** shard-distribution group — individually assignable to any shard, no file-boundary protection at all. A describe block with `beforeAll`/`afterAll` but no serial override falls into a `parallelWithHooks` bucket that gets explicitly chunked into `ceil(count / shardTotal)`-sized groups and CAN be split across shards. Only a `.serial`-configured block gets one shared group key end-to-end, and `filterForShard` (confirmed: groups are assigned to a shard wholesale via a running-count range check, never split mid-group) keeps that whole block in one shard. **Anyone adding a new test that assumes execution-order or same-worker adjacency with another test MUST wrap the pair in `test.describe.configure({ mode: 'serial' })` — nothing else in this repo's sharding setup provides that guarantee, and the file boundary alone is not protection.**

**Audit result: no genuine cross-test or cross-file ordering dependency exists in the current 23-file, 515-test suite.** Grepped every spec file for describe-scope (not test-scope) shared mutable state — the only 2 hits were false positives (local variables fully scoped inside retry-helper functions in `call-logs.rbac.spec.ts`/`deals.rbac.spec.ts`). The 2 files using `.serial` (`quotations.spec.ts`, `productsAndServices.spec.ts`) have no genuine data handoff between their tests — `git log` confirms Quotations' serial mode was added for QA-server load management under concurrent quotation creation (commit `0271e76`), not a data dependency; both are wrapped at the file's outermost describe, so they stay atomic under sharding regardless. Products & Services' 3 shared fixture records (`adminActive`/`restrictedActive`/`inactive`) are a deliberate globalSetup-to-all-tests pattern (not test-to-test) — safe under sharding because `globalSetup` runs once per shard and creates fixtures unconditionally fresh every run, so whichever shard(s) end up running `productsAndServices.spec.ts`/`.rbac.spec.ts` (the RBAC file has no `.serial` and could land on a different shard than the UI file) each get their own valid, independently-created fixture set. The only 2 `beforeAll()` usages in the suite (`reports.rbac.spec.ts:119`, `reports.spec.ts:162`) ARE shard-splittable per the mechanism above, but are safe by design — see the correction immediately below.

**Documentation-only correction needed, whenever `reports.rbac.spec.ts`/`reports.spec.ts` are next touched — not fixed now, per explicit request.** Both files' "run-count verification per entity type" describe blocks carry a comment justifying their use of plain `test.describe()` (not `.serial`) that states *"this suite always runs `--workers=1`"* and *"runs tests in declaration order within a single worker."* **Both claims are now factually incorrect** now that sharding exists — these blocks have `beforeAll` with no serial wrapper, so per the finding above they CAN be split across genuinely concurrent shard machines, with no ordering guarantee between the resulting groups at all. This is not a functional bug — the underlying test design is independently safe (each shard's own `beforeAll` produces a valid, test-preceding `windowStart` for whichever subset of the 8 tests it received, and the assertion is `toBeGreaterThanOrEqual`, not exact equality, deliberately tolerant of concurrent pollution per the file's own adjacent comment) — but the stated justification for why it's safe is stale and would mislead a future reader into trusting a no-longer-true premise. Correct the comment to cite the `>=`-assertion tolerance as the real reason it's safe, not the now-false single-worker/declaration-order claim, next time either file is edited.

### Retry-count discrepancy on first real sharded main run (Build #119, run `34357689027`) — investigated, mechanism confirmed, not a sharding/merge bug (2026-09-09)

A run reporting "22 retries, 3 flaky, 2 failed" looked arithmetically wrong (3+2 should mean ~5 tests needed retrying, not 22). Investigated with the actual merged `results.json` downloaded and parsed directly, not just the notification summary — root cause confirmed, not guessed.

**Root cause: Playwright's own documented serial-mode + retry semantics, not a merge-step bug, not double-counting across shards, and not internal in-test retry loops.** `quotations.spec.ts` wraps its entire 24-test file in `test.describe.configure({ mode: 'serial' })` (added 2026-06-25, commit `0271e76`, for QA-server load reasons unrelated to this). ### "Suite Drift Detected" false alarm on a clean run — same root cause as the "+449 passed" gap, fixed structurally, not with a third narrow carve-out (2026-09-09)

**Symptom:** the notification showed "⚠️ Suite Drift Detected" with a failure-level banner on all-passing runs — `dev` (33/33) and `sandbox` (which legitimately runs a different count every run via `detect-tests.sh`).

**Root cause (confirmed by reading real `ci/reporting-history` data):** `detectSuiteDrift()`/`computeDelta()` compared against whatever record ran immediately before in `history/${env}.jsonl`, which is keyed by **app environment**, not branch — `dev.yml` sets `ENV: qa`, so dev's 29–33-test `@smoke` runs and qa's 380–499-test `@regression` runs interleave in one file (a dev run's "previous run" was often a qa run → false `-466`, or a meaningless `+449` — the same bug as Build #239's "+449 passed" delta line). The earlier 2026-09-03 `isDevEquivalentRun` fix patched one trigger only (a `sandbox:reset` sharing dev's SHA), which is why this resurfaced.

**Fix — general mechanism, no per-branch/scenario carve-outs:** `computeDelta()` and `computeSuiteDrift()` now require the candidate previous record to share the **same branch AND the same normalized scope**. Scope is derived from the run's own results (never declared per workflow — an enumeration that would need a human to register every new branch/target, the exact failure mode of the 09-03 fix): `RunHistory.deriveTestScope(rawTitles, modules)` returns (1) `common-tag` — the one `@tag` (generic `/@[A-Za-z]\w*/g` scan, no hardcoded tag list) shared by every executed test, i.e. whatever `--grep @X` produced; else (2) `module-set` — sorted deduped `${type}:${name}` of modules that contributed a test (also makes suite growth safe: a new module changes the set, so the first run finds no comparable prior — honest silence, never a false alarm); (3) `empty-report` for 0 tests. Raw `--grep` strings / `detect-tests.sh` targets were rejected as the scope value (too many shapes, comparisons would fragment).

**Behavior worth knowing:** a new branch, a changed scope, or a first sandbox run for a new module combination simply finds no comparable prior record (silent, correct); drift fires only on a decrease (`totalDelta < 0`) within the same scope; concurrent same-branch+scope runs are unchanged (`syncHistory.ts`'s existing retry/backoff). **Backward compat:** pre-fix records lack `scope`, so none ever match; the first run per branch+scope logs `[syncHistory] Derived test scope: "<scope>" (basis: <basis>)` and becomes the baseline; comparisons resume from the second run, no backfill needed. Verified against the real 22-record qa history plus constructed cases (dev-vs-qa no longer alarms; Leads-only vs Deals-only sandbox scopes distinct; a same-scope 113→90 drop still fires; 499→515 growth does not).

**Severity fix (deliberate, not a leftover):** `computeOverallVerdict()`'s suite-drift branch keeps `verdict: 'blocked'` (tests silently vanishing is often a broken file — a false positive costs one confirmation, a false negative is far worse) but `bannerTone` changed `danger`→`warning`, so a 0-failed drift run renders amber instead of the same ❌ red as a broken run.

**Files:** `ReportParser.ts` (additive `allTestTitlesRaw`), `RunHistory.ts` (`deriveTestScope()`, scope-aware `computeDelta()`/`computeSuiteDrift()`, optional `RunHistoryRecord.scope`), `scripts/syncHistory.ts`, `AutomationHealth.ts`. No workflow/Jenkinsfile changes.

### A cross-process lock only protects workers on the SAME filesystem — formFields cross-shard config-mutation race, root-caused and fixed (2026-09-29)

**Root cause (confirmed, sandbox run `36520337903`, 8 shards, 898 tests, commit `9e35fc1`):** 6 genuine formFields failures (FFD15, FFTK38, FFRPS24, FFRTK7, FFRTK9, …) plus most of that run's 33 flaky tests trace to one mechanism — `formFieldLockFactory.ts`/`formFieldsTestLock.ts`'s lock is `fs.mkdirSync`-based under `.locks/<env>` on ONE runner's disk. The lock itself is well-engineered (heartbeat staleness, FIFO fairness — see §29) but only coordinates processes sharing one filesystem. GitHub Actions runs each shard on its own VM, so two shards each held "their own" exclusive lock while mutating the SAME account-wide custom-field config on the same staging account.

**Evidence (raw CI log, not inferred):** each entity's UI and RBAC files landed on different shards with overlapping wall-clock (e.g. `dealFieldLimits.spec.ts` on 6/8 and its RBAC file on 2/8 overlapped 8 min; FFD15 failed at the overlap waiting for a Min-Length input a concurrent Regex switch from the other shard had just disabled); `leadFieldLimits.spec.ts` itself was split across 6/8 and 7/8. FFTK38's post-cleanup read-after-write caught `regexLabel: expected "No Regex", got "Email"` — state nothing in its own file sets. FFRTK7 showed a real `HTTP 400` naming `cfFormFieldLimitText`. Flakes clustered on tests asserting the exact currently-configured state (Regex/valid-value), the only ones exposed to a torn read.

**Why it got worse in this run:** `9e35fc1` removed `.serial` from every formFields sub-block, reasoning the lock already prevents concurrency — true only for one filesystem. `.serial` had been (unacknowledged) keeping a block in one shard-distribution group; the UI-vs-RBAC cross-file race was always possible.

**Standing lesson — must not silently recur:** a cross-process file lock (`fs.mkdirSync`, `fs.rmSync`, any local-disk primitive) only protects workers sharing one filesystem; sharding runs shards on separate machines. Any suite relying on such a lock for correctness must be structurally guaranteed to never split across shards. `.serial` is necessary but not sufficient (it never covers two separate files targeting one shared resource); the real guarantee must come from (a) eliminating the shared mutable resource (dedicated, disjoint fields per consumer — cf. `ab06f5e`), (b) a genuinely cross-machine coordination mechanism, or (c) structurally keeping dependent tests on one shard. "The lock already prevents concurrent execution" is a claim about workers, not CI topology.

**Fix (sized to hold regardless of shard count/reshuffling):**
1. **CI carve-out** in `sandbox.yml`, `qa.yml`, `stage.yml`, `main.yml` (the only 4 pipelines that shard the full/regression suite; `prod.yml` is unsharded `@prodSafe`, which formFields tests never carry; all 5 Jenkinsfiles are `agent any` with no `parallel{}`/`--shard`, so the local lock is already fully correct there). New `run-formfields-tests` job: a fixed 6-entry matrix (`lead`/`contact`/`company`/`deal`/`task`/`productsAndServices`), each running that entity's UI+RBAC pair together via explicit file paths — never Playwright's count-based `--shard`. The rest-of-suite track excludes formFields (initially `--grep-invert "formFields"`, since replaced by the planner's hardcoded path-prefix exclusion — see "Dynamic per-module shard planner"). In `sandbox.yml` the carve-out runs only on the escalated `--grep @regression` path (the only case that shards); its "Verify all shards reported" check expects the extra 6.
2. **`.serial` restored** per field-mutating sub-block in each UI file, and (2026-10-05) per-category sub-blocks in each RBAC file (Text/Number/Paragraph/Regex/dual-fixture/Cache; the read-only lock-free block untouched) — defense-in-depth for same-shard interleaving, scoped per sub-block so one failure no longer skip-cascades unrelated fields.

**Numbers:** formFields is 417 of 932 tests (399 of 898 under `@regression`). Per-entity UI+RBAC time at workers=2 ranged 79.7 min (Products & Services) to 110.5 min (Lead) → ~90–130 min track vs a 180-min timeout; wall-clock roughly neutral, cost is ~2–3 extra per-job npm-ci/browser-install overheads.

**Second-order effect, same day (sandbox run `36537195806`) — globalSetup 429:** the carve-out raised peak concurrent `globalSetup` jobs from 8 to 10 within ~35s; 9 succeeded, the last-starting Lead job failed `GET /products/layout?view=create` with HTTP 429 before any test ran (the 8-job run had zero such failures; the previous run's 33 flakes had zero 429s, so this is a separate mode). `ensureProductFixtures()` makes 5 unprotected calls with no retry (layout, currencies, 3× `POST /products`). **Fix:** `withTransientRetry()` in `globalSetup.ts` (3 attempts/backoff mirroring `setupRole()`; retries only 429/5xx, never real 4xx) wrapping `loadProductReferenceData()` and `createOneProductFixture()` (module-private, one call site each). Rejected capping `max-parallel` (would double the track's wall-clock for a failure a bounded retry absorbs). Revisit only if a run shows the retry insufficient.

**Not fixed, correctly out of scope:** ~200+ `net::ERR_ABORTED` on the `.../fields?entityType=...` endpoint family (FormFieldsConfigPage's post-mutation re-poll aborted by navigation) is a candidate for `errorFilters.ts`'s `ABORT_ON_NAVIGATE_PATTERNS`, but needs the usual zero-correlation-with-real-failures evidence bar first (a few co-occur with the race above as a downstream symptom). The 4 "recurring" Companies/Products & Services Hide-Empty-Fields failures match the separate Quotations auto-reveal timing outlier (below).

**Verification status:** `tsc`/`eslint` clean; all 4 workflow YAMLs parsed and actionlint-clean (WASM engine, confirmed to catch deliberately broken copies); `--grep-invert`/shard arithmetic checked against real `--list`. **Not verifiable locally:** a real GitHub Actions run — watch for 6 formFields shards each running its UI+RBAC pair, the rest-of-suite shard count matching the real excluded total, and `sandbox.yml`'s shard-verification check passing.

### OPEN, flagged not fixed — formFields' fixed 6-shard matrix does not self-scale with test-count growth

### Dynamic per-module shard planner — replaces blind count-based `--shard=N/M` for the rest-of-suite track (2026-09-29)

**Problem:** the rest-of-suite track's `--shard=N/M` is Playwright's count-based splitter with zero awareness of file boundaries or shared state — the mechanism behind the formFields cross-shard race. formFields got a hand-built carve-out, but nothing stopped the next shared-state feature from needing another one-off (the enumeration fragility `deriveTestScope`'s WHY comment already warns about).

**Design (Option A — formFields matrix left untouched):** `scripts/plan-shards.ts` discovers tests via `npx playwright test --list --reporter=json <target>`, **excludes any file under `ui/formFields/` or `rbac/formFields/` via a hardcoded path-prefix check** (not a CLI flag, so no caller can omit it; chosen over `--grep-invert "formFields"` per rule 17 — a substring match fails silently if a title/path elsewhere ever contains it, a path-prefix check fails loudly; cross-checked against both methods on `@regression` scope (499 tests/23 files), full scope (515/23) and a positive control (exactly the 12 formFields files/417 tests)), then bin-packs the remaining files first-fit-decreasing into 125-tests/shard bins (the budget from measured 1.380 tests/min at workers=2 → ~90 min). It writes `shard_total`/`shards_json`/`test_count` to `$GITHUB_OUTPUT`; `run-tests` consumes `matrix.shard.files` (`${{ join(matrix.shard.files, ' ') }}`) via the existing `fromJSON` matrix mechanism; artifact names use `${{ matrix.shard.shardId }}`. No single non-formFields module exceeds the budget (largest, Reports, is 65), so a module's UI+RBAC pair is never split by the planner itself.

**Real results:** `--grep @regression` → 5 shards (125/124/124/119/7), zero formFields files; full scope → 5 shards, 515 tests. Qa going 4→5 shards (a 7-test remainder file couldn't fit without exceeding the target) leaves the critical path unchanged (largest shard still 125 tests, ~90.6 min); the only cost is one extra job's ~5–8 min fixed overhead (~1.5–2% more billed minutes).

**`sandbox.yml`'s decide step deliberately has two branches:** only the escalated (`TARGET == "--grep @regression"`) branch calls the planner. The small-selective branch stays planner-free because `detect-tests.sh` can select formFields paths directly for a formFields change, and the planner's hardcoded exclusion would silently drop them; it emits `shards_json=[{"shardId":1,"files":[],"testCount":N}]` (empty `files` = fall back to `$TARGET` + `--shard=1/1`, unchanged), and `run-tests` branches on empty `files`.

**Bug caught in local testing:** `extractJson()` first matched a `{` inside dotenv v17's startup banner (`… { override: true }`) instead of Playwright's JSON root; fixed by requiring the `{` at start-of-string or after a newline.

**Verified:** real `--list` runs; `GITHUB_OUTPUT` write path against a temp file; an unmatchable `--grep` exits 1 with `::error::` and writes nothing; `tsc`/`eslint` clean; all 4 workflows actionlint-clean. **Not verifiable locally:** a real Actions run — watch for the expected shard count with non-empty file lists, per-shard `--grep @regression` re-filtering, and merge-and-report artifact patterns (`blob-report-<workflow>-<shardId>`) matching.

### `productsAndServices.rbac.spec.ts:20` (PS6) "browser closed" failure — root-caused with direct log evidence, NOT caused by increased concurrent job count, fixed at both the immediate and structural level (2026-09-30)

Investigated together for a shared cause before treating as 4 separate bugs, per explicit direction. Confirmed NOT the already-known 429 page (`isRateLimitedPage()`'s pattern never matched) — a DIFFERENT, generic Kylas frontend error-boundary/fallback component, confirmed live in two shapes: `<span class="error-msg">Something is broken here</span>` scoped to a single card (Company's case) and `<div class="app-error something-is-broken">` scoped to the entire `#app` root (Task's case, confirmed via 787 combined retry attempts all reporting the identical intercepting element). Both `misc-errors.json` captures for these jobs showed zero relevant `pageerror`/`console-error` entries — consistent with a React error boundary swallowing the underlying failure internally rather than letting it bubble to an uncaught-exception handler. Root cause of *why* the underlying component fails is not established (out of scope for a test-code fix, CLAUDE.md rule 10) — this is a defensive hardening fix for the resulting known bad UI state, not a proven root-cause fix for the app's own issue.

**Fixed:** `authManager.isAppErrorBoundaryPage()`/`tryRecoverFromAppErrorBoundary()` (text-match `/something is broken/i`, plain reload — no "Refresh" button was present in either captured occurrence, unlike the 429 page). `BasePage.withRateLimitRecovery()` now checks both conditions in the same catch block (deliberately NOT a third separate combinator — both conditions need the identical remedy, reload-and-retry-once, so this is the correct application of "one job," not a violation of the earlier one-function-one-job reasoning). This means every ALREADY-wrapped call site (`clickDetailPageTab()`, `waitForEntityListPage()`, `FormFieldsConfigPage.open()/searchField()/openFieldForEdit()`, `ProductsAndServicesPage.goToCreateProductForm()`) gets this protection for free — Company's FFRCO13 (`clickDetailPageTab()`) is fixed by this alone. Three genuinely NEW uncovered call sites were also found and wrapped: `TasksPage.selectReactSelectOption()`'s final option click (Task's FFRTK7/FFTK8), `FormFieldsConfigPage.submit()`'s navigation-back assertion (Task's FFRTK6 — stuck on the edit URL for the full 120000ms instead of returning to the list), and `ProductsAndServicesPage.openProductForEdit()`'s Name-input assertion (PS's FFPS24/FFPS21 — Name input entirely absent from the DOM, consistent with the same class even without a captured intercepting-element name, since this assertion never clicks anything).

**Verified:** `tsc --noEmit`/`eslint` clean on all 5 touched files. **Not verifiable from here:** a real re-run of these exact tests in CI.

### CI load reduction — sequenced tracks, conditional product-fixture creation, recovery-event measurement (2026-10-06)

**Why:** the 2026-09-29 formFields carve-out made core shards and the 6 formFields shards start together (10–11 concurrent jobs per workflow, each running `globalSetup` against the same shared backend) and produced the 429 / error-boundary failures above. Four changes cut that load and measure whether it helped. **Not verified by a real run** — `actionlint` checks syntax/expressions only (0 issues on all 4 workflows; 3 deliberately broken control copies — a typo'd `needs:` job, a malformed `if:` expression, a misspelled job-output property — were each caught), never runtime job-graph behavior. The first real run is the proof.

**1. formFields starts only after the core shards finish** (`qa.yml`, `stage.yml`, `main.yml`, `sandbox.yml`): `run-formfields-tests` gets `needs: [run-tests]` (sandbox: `[detect, run-tests]`) and `if: ${{ !cancelled() }}` (sandbox: `&& needs.detect.outputs.run_formfields_track == 'true'`, gate kept). `needs` alone would apply the implicit `success()` and skip formFields on any core failure; `!cancelled()` runs it after run-tests ends in ANY result. Job graph, per workflow: (a) all core shards pass → formFields runs; (b) one core shard fails → run-tests is `failure`, formFields STILL runs, merge-and-report runs (`always()`, `needs` both); (c) run-tests skipped (qa/stage/main: only if `plan` fails; sandbox: only if `detect` fails, and then `run_formfields_track` is empty so formFields skips exactly as before) → formFields runs in qa/stage/main, skips in sandbox by its own pre-existing gate. A formFields-only sandbox change takes the non-escalated path (`run_formfields_track=false`; its formFields specs run inside run-tests via `$TARGET`), so run-tests is never skipped there. Only a human cancelling the run stops formFields. merge-and-report and sandbox's shard-completeness check (6 extra formFields reports expected when the track is on) are unchanged. **`main.yml` caveat:** all three jobs carry `environment: production`. If that environment has required reviewers, formFields (now ready only after run-tests) raises a SECOND approval prompt — merge-and-report already raised one after both tracks. No deadlock (a pending approval blocks only its own job and what `needs` it), but an unattended pending approval holds the run. Whether reviewers are configured isn't knowable from the repo. **Cost:** wall-clock ≈ 2x. **Revert:** delete the `needs`/`if` lines (and their WHY comments) from `run-formfields-tests` in the 4 files.

**2. `max-parallel` — evaluated, NOT added.** After change 1 each stage is 5–6 jobs and the two tracks never overlap inside a workflow; the earlier evidence is that 9 of 10 concurrent `globalSetup`s succeeded and `withTransientRetry()` absorbs the straggler, so a cap would add wall-clock for no demonstrated benefit. Cross-workflow overlap (qa + stage + sandbox) is the remaining exposure and is the separate open `concurrency:` item above. Revisit only if the new load-signals table shows 429s still clustering at high job counts.

**3. Product fixtures are created only when the invocation may run a Products & Services spec** (`src/auth/productFixtureNeed.ts`, wired into `globalSetup.ts`). Mechanism, verified with a scratch Playwright config: `globalSetup` runs in the main runner process, so `process.argv` holds the real CLI (`["test","-c",…,"t/a","--grep","@x","--workers=1"]`); Playwright's public `FullConfig` exposes no file filters. Fixtures are skipped ONLY when positional file filters are present, unambiguous (value-taking flags like `--grep @x` are skipped explicitly), and match none of the fixture-needing specs — found by scanning the test dirs for specs that import `productFixtureAccessor` OR have `productsAndServices` in their path (so a future reader is picked up automatically, and the Products & Services formFields shard keeps its fixtures as requested). Every ambiguous case (no filters, grep-only, unknown token, no test command, no candidates found) → create. Decision table checked on 12 synthetic command lines: Lead/Quotations/Deals-only file lists skip; P&S formFields shard, a core shard containing either P&S spec, `tests/ui`, whole-suite, grep-only, unknown flag, `show-report` create. **Failure mode:** on skip, any stale `src/data/productFixtures/<env>.json` is deleted, so a wrongly-skipped P&S test hits `getProductFixture()`'s existing "no fixture file found" / "fixture not found" throw instead of reading stale data. **Finding:** only `tests/ui/productsAndServices/productsAndServices.spec.ts` and `tests/rbac/productsAndServices.rbac.spec.ts` call `getProductFixture()` — the Products & Services *formFields* specs don't, so that shard's fixtures are created unnecessarily (kept on explicit instruction; tighten the path rule in `needsFixtures()` to stop). No other caller of `ensureProductFixtures()`/the accessor exists. **Saves** ~5 requests per formFields shard × 5 shards. **Revert:** replace the `selectionNeedsProductFixtures` block in `globalSetup.ts` with the bare `await ensureProductFixtures();`.

**4. Load signals measured** — per shard, counts of the app's 429 page, the "Something is broken" boundary (with recovered/failed outcome of the retried action), and `globalSetup` transient retries, shown in the email's "CI Job Stats" card as a "Load Signals by Job" table (start–end UTC, counts, and test jobs running concurrently over the job's window / at its events). Reuses the existing pipeline: `ErrorCollector.recordRecoveryEvent()` → worker file → `MiscErrorReporter` merge → `merge-misc-errors.ts` (attributes events to a shard from the artifact directory name, lists every shard that reported even with zero events) → `miscErrors.recoveryByShard` → `JobStats.buildJobRecoveryRows()` → `EmailTemplate`. All new report fields are optional/additive. **Found while building:** `globalSetup` runs BEFORE `MiscErrorReporter.onBegin()`, which deletes every `misc-errors-worker-*.json`, so main-process events use their own file (`recovery-events-main.json`, truncated by globalSetup, merged and removed by `onEnd`). The same ordering means `ErrorCollector` captures from `globalSetup`'s node listeners are written to a pid-named worker file that `onBegin` deletes — a pre-existing gap, NOT fixed (rule 11), flagged here. **Shared-helper ripple check:** `BasePage.withRateLimitRecovery()` (22 call sites) only gains outcome recording around its existing single retry; `tryRecoverFromRateLimit`/`tryRecoverFromAppErrorBoundary` have that one caller; `withTransientRetry()` has 2 call sites in `globalSetup.ts` and gains one pre-sleep recorder call. End-to-end synthetic: real child processes (main + worker) → real `MiscErrorReporter.onBegin/onEnd` → real `merge-misc-errors.ts` on 3 shard directories → real `EmailTemplate` (counts attributed to the right jobs, a shard with no events field shown clean, a missing shard shown "(no shard data)", empty and legacy-shaped reports render). Lint adds 2 `no-console` warnings (in files already using `console`), 0 errors. **Revert:** remove the three `recordRecoveryEvent` call sites and `resetMainProcessRecoveryEvents()`; the report fields and email section then render nothing.
