This is the accumulated, evidence-based record of every significant bug class, architectural fix, and investigation conducted on this codebase — consolidated from the former `.claude/known-issues.md` and `.claude/INVESTIGATION_LOG.md`. For confirmed **Kylas application** bugs specifically, see `APPLICATION_BUGS.md` — this file covers everything else: code bugs found and fixed, architectural overhauls, and flakes investigated but not conclusively resolved.

### Session-expiry recovery — full architectural history

This bug class was independently fixed **five separate times** before the final overhaul below (`click()`/`fill()` 2026-07-09, `navigateTo()` 2026-07-20, `armResponseWaitWithRecovery()`/`withSessionExpiryRetry()` 2026-07-20, then the two gaps below). A full-codebase grep eventually found **80 further raw `expect(...).toBeVisible/toHaveText/toHaveURL` calls** written directly in module page objects (Contacts 18, Companies 19, Deals 23, Leads 12, CallLogs 4, Tasks 3, Quotations 1) — every one silently unprotected. This is the exact anti-pattern where per-method retry wrapping keeps getting forgotten by new code — the same shape already solved once before via `src/utils/navigation.ts`'s `safeWaitForURL()` consolidation (three independent bare-`page.waitForURL()` bugs, each rediscovered only after a confusing CI failure).

**Phase 1 — verified against the real app, not assumed.** No cookie-based session at all — clearing `localStorage` alone immediately redirects to `/signIn`. Login is `PUT {apiBaseUrl}/users/login`, response `{token}` — a JWT stored in `localStorage.token`; every API call sends `Authorization: Bearer <accessToken>` from inside the decoded payload. The JWT's `refreshToken` field has no usable refresh endpoint — three plausible candidates all returned bare, header-less 400s. A concurrent re-login with valid credentials returns the identical `accessToken` and doesn't invalidate the first — concurrent logins are server-side safe.

**Phase 2 — a `page.route()` network-interceptor design was built, verified to partially work, then deliberately abandoned (not shipped broken).** The core mechanism worked (401 detection, dedup, retry all correctly), but a broader regression sample showed `route.fetch()` itself — even on requests nowhere near a 401 — broke completely unrelated saves with generic `HTTP 400 "Unexpected error occurred!!"` errors. A/B tested decisively: no interceptor = clean; interceptor registered but `route.continue()`-only = clean; `route.fetch()` actually used = breaks. Root cause (well-evidenced, not fully proven): replaying via Playwright's Node-side networking instead of the browser's native stack gets flagged by the backend. **`route.fetch()`-based interception is unusable for this app.** Immediately neutralized before doing anything else.

**Phase 3 — what was actually built: one shared combinator, not 80 hand-rolled fixes.** `BasePage.withSessionExpiryRecovery<T>(fn: () => Promise<T>): Promise<T>` — capture the URL *before* the call (the page may already be on the failure page by catch-time); on catch, check registration + expiry-page condition; if matched, recover once and retry `fn()`; otherwise rethrow unchanged. All 80 raw call sites became one-line changes; `BasePage`'s own generic helpers (`waitForVisible`, `waitForHidden`, `waitForUrl`, `assertVisible`, `assertText`, `assertFormErrorToast`) now route through it too.

**Phase 4 — a second real gap found via the combinator's own verification, fixed the same way.** Deliberately reproducing `withSessionExpiryRecovery()` (corrupt the token, force a fresh render) surfaced a distinct **"Forbidden"** client-rendered bootstrap page with the URL completely unchanged — a state `isSignInUrl()`'s URL-only check can never recognize. A mid-session expiry redirects to `/signIn`; a fresh page load/reload with an already-invalid token hits a different bootstrap-time auth-check code path that renders "Forbidden" instead. Grepped the whole codebase for any test relying on this exact page as an expected RBAC-denial outcome — zero hits, so recognizing it as an expiry symptom cannot mask any real assertion. Fixed by adding `authManager.isSessionExpiryPage(page)` (URL OR body-text check) and updating **all five** gate checks (`click()`, `fill()`, `navigateTo()`, `assertUrl()`, `withSessionExpiryRecovery()`) to use it.

**Phase 5 — a proactive layer added on top: prevent the failure, not just recover after it.** `AuthManager.ensureFreshSession(page, role)` reads the JWT's own embedded absolute expiry (`payload.data.expiry`) and proactively refreshes via a fast headless login if less than **10 minutes** remain — grounded in this codebase's own timing data (max observed heaviest-flow duration ~2.1 min, so 10 min gives ~5x margin while being ~1.6% of the token's ~10.4h lifetime). Wired into `fixtures/index.ts`'s `createRolePage()`. Deliberately never uses `route.fetch()`/request-replay, so it can't hit the Phase 2 rejection.

**This mechanism's first real-CI execution (sandbox run `30286886093`, 2026-07-27) exposed a much more mundane bug than the elaborate theories initially suspected.** `loginHeadless()`'s comment asserted `config.apiBaseUrl` "already includes `/v1` for every environment" — true only for the local `.env` copy, never cross-checked against the CI secret backing the same variable. 64 of ~90+ sandbox failures and 98 of a separate qa-regression run's failures were the identical `HTTP 404 from /v1/users/login`. Confirmed mechanistically: `curl -X PUT https://api-qa.sling-dev.com/v1/users/login` → 401 (real route, correct); the identical call without `/v1` → 404. **Fixed** via `AuthManager.getLoginUrl()`, later consolidated into the shared `config.buildApiUrl(path)` (see below) — normalizes the base URL regardless of which shape a given environment's secret happens to use.

**SECOND occurrence of the exact same normalization bug, found one day later — in a call site the first fix's own ripple-check had already grepped and missed.** `DealsPage.fetchCurrentDealApiData()` built its URL as `${config.apiBaseUrl}/deals/${id}` — same unqualified-`/v1` assumption. Direct proof: `GET {base}/v1/deals/430321` → 200; `GET {base}/deals/430321` → 404, silently swallowed by `if (!res.ok) return null` with **zero logging on either branch** — meaning every caller of this method got false negatives in CI regardless of whether a contact was actually associated. **Root cause of the miss, stated plainly:** yesterday's grep DID surface this exact line, but it was pattern-matched and dismissed as "logging only" without actually reading what it does — finding a match is not the same as understanding it. **Fixed by consolidating into one shared canonical utility** — `config.buildApiUrl(path)` — instead of a third independent copy, mirroring the `safeWaitForURL()` precedent. Logging added on both branches, closing the silent-failure gap. This bug's downstream effect on the Deal Contact-persistence investigation is covered in `APPLICATION_BUGS.md`'s "Investigated but not confirmed" section (that entry was itself later retracted 2026-08-11 as no-longer-reproducible — see below).

### ID-capture and response-matching bug class

**Confirmed false-positive bug, found in 3 places, fixed:** `DealsPage.captureDealIdFromResponse()`, `CompaniesPage.captureCompanyIdFromResponse()`, and a third instance in Deals' "add quotation from deal panel" flow all used a bare `.includes('/deals')`/`.includes('companies')`/`.includes('/quotations')` substring match with no version prefix — each could match an unrelated background analytics/reports POST (confirmed live: `/v4/reports/deals`) that raced ahead with no `id` field, silently capturing `null` and throwing a false "save failed silently" error despite a genuine success toast (e.g. "Quotation created (Quotation ID: 8794)"). Fixed all three by requiring the real `/v1/<module>/` path and excluding `/reports/`. **If you add a new `captureXxxIdFromResponse()` anywhere, require the versioned path from the start.**

**Session-expiry recovery for `waitForResponse()` ID-capture — two real bugs found via deliberate reproduction before trusting the design:**
1. **A race in the original flag-based coordination.** `armResponseWaitWithRecovery` used to set a WeakMap flag only *after* fully awaiting its own recovery (10+ seconds). For methods shaped like `LeadsPage.saveLead()`, code reacting to the same failure much faster (`assertNoFormErrors()`, ~1.5s) could throw and propagate before the flag was ever set — reproduced live via a synthetic `page.route()`-injected 401. Fixed by redesigning `armSessionExpirySignal()` to expose a synchronous `hasFired()` boolean, toggled the instant the event arrives.
2. **A competing-navigation race in `tryRecoverSessionForPage()` itself.** The app's own frontend can independently fire its own client-side redirect to `/signIn` in reaction to the same 401 — reproduced live as `net::ERR_ABORTED; maybe frame was detached?` immediately after the injected 401. Fixed with a single bounded retry keyed on this exact signature.

`withSessionExpiryRetry(workflowFn, description)` wraps an entire top-level workflow method and retries the whole thing once on detected expiry — **deliberately NOT applied** to share/reassign/clone/add-from-panel methods (a dedicated 4-agent investigation confirmed these assume the page is already on a specific entity's detail view; a blind retry after a recovery navigation would fail worse than today).

### Navigation-drift gap across 6 modules — confirmed and fixed (2026-07-27)

**The confirmed gap:** every `waitForXDetailsPage()`/`waitForListReady()` across Deals, Companies, Contacts, Leads, Tasks, and Quotations independently duplicated the same shape — `waitForUrl()` (resolves the FIRST moment the URL matches, no guarantee it stays matching) followed by an entity-GET wait wrapped in `.catch(() => null)`. Under heavy concurrent load, the app's own client-side router can bounce away from the just-matched URL before that GET ever fires — the silent catch swallowed this completely. The real failure then surfaced much later as a generic element-not-found timeout with zero diagnostic signal.

**Full-codebase sweep before fixing:** confirmed identical shape in Companies/Contacts/Leads (list + detail variants) and Tasks/Quotations (detail variant only). Checked Meetings/Call Logs — confirmed **no** matching gap.

**Fix:** two new shared `BasePage` methods, `waitForEntityDetailPage()`/`waitForEntityListPage()` — one canonical reload-and-retry implementation instead of 6 independently-drifting copies. Every module's own method refactored to a thin wrapper. **Fast-failure guarantee, explicitly verified:** absolute theoretical worst case ~190s (~3.2 min), a ~60% reduction from the previous unbounded 480s, always with a clear diagnostic message instead of a bare generic timeout. For the actual bug pattern (URL matches, then redirects away), realistic time-to-clear-failure is ~35-40s.

**A second, genuinely different bug found along the way:** re-verifying after the navigation-drift fix, the Quotation-permission test still failed, but now in 2.0 min with a clear validation error instead of an 8-minute silent timeout. Traced to `DealsPage.getAssociatedContactId()`/`getAssociatedContactName()`/`getAssociatedCompanyName()` having **no explicit timeout at all** (this codebase never sets `actionTimeout`, whose real Playwright default is 0/unbounded). Fixed by adding an explicit 10s bound to all three reads.

**Zombie session-expiry listener race — the same investigation's third finding.** `waitForEntityListPage()`/`TasksPage.waitForListReady()` raced `armResponseWaitWithRecovery(...)` against a plain table-visibility wait via `Promise.race` — which never cancels its losing branch, only abandons it. Since the table-visible branch almost always wins first, the abandoned expiry-listener-arming promise could keep listening for up to 60s after the calling method returned, ready to fire a wrongly-targeted recovery if a real expiry landed in that window — confirmed via a real full-suite run where TWO unrelated recovery attempts fired within 3ms of each other for calls that had already returned 27-54 seconds earlier. **Fixed** by swapping in a plain, listener-free `page.waitForResponse()` for the race's response branch — 100% behavior-preserving for list-readiness, only removing the dangerous unused side channel. Structural fix, not a forced-reproduction one: several deliberate repro attempts confirmed the hazard exists by construction but didn't cleanly reproduce the exact 27-54s survival window on demand.

### Random-option-pick dropdown hangs — generalized fix across 5 modules

`DealsPage.selectFirstOptionFromDropdown()`'s first fix (bounded 15s retry on a stuck option click) covered one symptom but not the bug class: 6 other call sites across `DealsPage.ts` (product row, associated contact), `TasksPage.ts`, `CallLogsPage.ts`, `MeetingsPage.ts` picked a random react-select option via the same unbounded `textContent()`+`.click()` shape. Also found: retrying the *same* index is sometimes futile — one specific index can be persistently non-actionable while every other index works fine. Both fixed via one shared `BasePage.selectRandomOptionWithRetry(options, description, opts?)` — 3 attempts, each bounding read+click to 15000ms, each **re-rolling a fresh random index**. **If you add a new "pick a random option from an open react-select menu" call site anywhere, use this shared method.**

`DealsPage.fillDealForm()`'s associated contact/company selection is **random by design**, a deliberate 2026-07-05 fix for a CI-hang problem — not itself a bug, but it means any new Deals test where ownership matters must pass `associatedContactName`/`associatedCompanyName` on `DealData` instead of relying on the random pick.

`BasePage.fillSearchAndWaitForOptions()` retries a react-select search on a transient DNS/network blip only — `TRANSIENT_NETWORK_ERROR_PATTERNS` is a deliberately narrow allowlist (DNS/connection reset/refused/timeout/unreachable), explicitly excluding real HTTP 4xx/5xx and routine `ERR_ABORTED`. **Do not widen this allowlist without the same live-evidence bar.**

### Locator/timing fixes catalog (by module)

- **Lead multi-select "chip drop"** — `selectRandomFromMultiValueReactSelect()` used to silently drop a previously-landed chip. Root-caused via `document.elementFromPoint()` instrumentation: the "reopen menu" click landed on the control div's center, which drifts onto a previous chip's remove icon as chips wrap onto multiple lines. Fixed by targeting the control's own `<input>` child instead.
- **Company Phones field collision (Lead)** — `phoneInput = () => page.locator('input[id*="input_phone_0"]')` was a loose substring match that also matched Company Phones' first entry. Company Phones was removed; the underlying fix (switching to the exact `name="phoneNumbers[0]"` attribute) was applied to all three modules with the identical fragile pattern (Leads, Contacts, Companies), not just Lead.
- **GPS trigger is section-scoped, not page-wide** — Lead's form has two "Get GPS Address" triggers with identical visible text; an unscoped `page.getByText(...)` throws a Playwright strict-mode violation. `BasePage.getFormSectionContainer(sectionHeading)`/`getGpsAddressTrigger(sectionContainer)` scope the click and throw a clear error on ambiguity instead of silently falling back to `.first()`.
- **`escapeRegExp()` duplicated privately across 5 page objects** — byte-for-byte identical in `DealsPage.ts`, `CompaniesPage.ts`, `ContactsPage.ts`, `LeadsPage.ts`, `TasksPage.ts`. Moved to one shared `protected BasePage.escapeRegExp()`.
- **`QuotationsPage.ts` per-row DOM-read loop** — three methods looped every list row with an individual `.innerText()` call. Replaced with one batched `allTextContents()` call — 6.4×–38.2× faster across QA/Staging/Prod in 9 timing runs. **If you find a `for (...) { locator.nth(i).innerText() }` pattern anywhere else, this is the fix.**
- **`CallLogsPage`'s Associated Deal field** — intermittent "zero options after retries" was a **data-linkage** problem, not a search-index-lag race: `ensureOwnedDealExists()` created the deal with no `associatedContactName`, so it got linked to a random, unrelated contact per the random-pick behavior above — no amount of retrying could find a deal never actually related. Fixed by threading the contact's name through to `generateDealData({associatedContactName})`. **A second, independent instance of this exact "mis-suspected as search-index lag" pattern was found 2026-08-23** — `BasePage.searchAndSelectByName()`'s truncated-to-first-word search term for Products & Services fixtures; see the Sandbox Build #144 investigation section below for the full write-up. Two confirmed occurrences now — treat "index lag" as a hypothesis to disprove first, not a default explanation, whenever a live search unexpectedly returns zero/wrong results.
- **`fillEditForm()` asymmetry (Lead vs. Contact) is real and intentional, not a bug:** Lead's `fillEditForm()` does NOT update Timezone, Country, or the 5 Professional fields (deliberately scoped to firstName/lastName/Salutation/Requirement/custom-fields only); Contact's DOES re-fill Timezone/Company. Open decision for a maintainer: extend Lead's edit coverage (riskier — react-select re-selection on a pre-filled form is exactly where subtle bugs live) or accept as create-only. Currently left as create-only.

### CL21/CL23/TC23/TC21/TK24/CL22/CL24 — sandbox CI code-bug investigation (2026-08-02/03)

Sandbox CI run `30706489847` (commit `26593ea`) surfaced 7 test failures. All 7 were **code bugs**, not app or environment issues, each re-verified live before fixing:

- **CL21/CL23 (shared root cause) — React Select dropdown pointer-event interception.** `CallLogsPage.fillPhoneNumber()`'s `phoneControl.click()` failed with "Target element... intercepts pointer events. After 209+ click retries..." — the dropdown menu was open from a prior interaction. Fixed with `openDropdownById()` + `force: true` (JS event dispatch avoids the interception). CL23 additionally had a second, distinct interception during `fillEditForm()`'s "Other Details" tab click — fixed the same way (`force: true`). Both verified 3/3 stable after fix.
- **TC23 — hardcoded `waitForTimeout(200)` calls stacking cumulatively** in `BasePage.selectDateTimeCustomField()` (3 calls after each time-picker column click), pushing an 8.1-minute test 6 seconds over the 480s timeout. Fixed by removing all three blind waits and replacing with one condition-based wait for `.rc-time-picker-panel` to become hidden after pressing Escape — the same pattern already proven in `MeetingsPage.fillTimePicker()`.
- **CL22 — unscoped "Log a call" button locator** (`button.btn.btn-primary` filtered by text, page-wide) could match the wrong button. Fixed by scoping with `.first()`.
- **CL24 — validation-error locator pattern too narrow**, missing a broader error-toast class already used elsewhere in the same file. Fixed by adding `.alert-danger:visible` to the selector.
- **TC21 — missing session-expiry recovery** on a tab click in `assertTaskCustomFieldsOnDetail()`. Fixed by wrapping in `withSessionExpiryRecovery()`.
- **TK24 — unbounded `expect(timeInput).toBeEnabled()`** could hang the full test timeout if the time input never enables. Fixed with a non-blocking `isEnabled({timeout:5000}).catch(() => false)` + warning log — fails fast with diagnostics instead of hanging.

**Call Log custom-field validation (2026-08-03) — confirmed NOT a bug.** The backend simply does not enforce character-limit/format validation on Call Log custom fields yet (unlike Meeting/Quotation/Task, which do). The corresponding test is `test.skip()`-ed with a comment pending future backend work — see `tests/ui/call-logs/call-logs.spec.ts` near the CL24 test.

### 5 sandbox failures (CL39, CL32, CL33, D28, Q-detail-verify) — full root-cause investigation (2026-08-09)

Sandbox CI run `31269450132` (2026-08-08, commit `95e602e`, confirmed real `--workers=2`/298 concurrent tests — `sandbox.yml` dynamically sets `WORKERS=2` whenever the selected test count exceeds 50) surfaced 5 test failures across Call Logs, Deals, and Quotations. All reproduced live on staging before any fix (no guessing):

- **CL39 (`call-logs.rbac.spec.ts:698`, "restricted user can update call log custom fields") — a real, deterministically-reproduced test-data bug, initially mis-suspected as a "date-time picker hang."** The actual failure (`Test timeout of 480000ms exceeded` + `locator.click: Target page, context or browser has been closed` inside `CallLogsPage.selectFromDropdown()`, stuck on `1_31_input_callType`) had nothing to do with any date/time widget — `fillCallType()` runs before custom fields in `fillEditForm()`. Root cause: the test generated `originalData` and `updatedData` via two independent `generateCallLogData()` calls with no `entityType` pinning — `entityType` (Lead vs Contact/Deal) determines which `callType` option text is valid ("I called the Lead"/"Lead called me" vs "I called the Contact"/"Contact called me"), and `fillEditForm()` never changes entity type on edit. An independently-randomized `updatedData.entityType` had a real chance of producing a `callType` option that simply didn't exist in this call log's dropdown, and `selectFromDropdown()`'s option click had **no timeout at all**, hanging the full 480s. **Confirmed via deliberate deterministic reproduction** (forced `originalData.entityType: 'Lead'`, `updatedData.entityType: 'Contact'`) — identical failure signature. **Fixed**: pinned `updatedData`'s `entityType` to `originalData.entityType` in the test, plus added explicit `waitFor`+`timeout` bounds to `selectFromDropdown()`'s option click (and the sibling `fillEntityType()`'s identically-unbounded option click, found via the same locator-reviewer pass). Verified 3/3 clean on staging.
- **CL32/CL33 (`call-logs.rbac.spec.ts:508`/`:530`, admin-role "Log a Call form did not open after 5 attempts") — confirmed NOT a code bug in `openLogACallForm()`'s retry logic; strongly correlated with a genuine Kylas app-side JS race under concurrent access.** Reproduced CL32 cleanly 2/2 in true single-worker isolation (opens on first attempt both times) — ruled out a straightforward logic bug. Deliberately re-running the full spec file with `--workers=2` on staging (matching the real failing CI config) captured a live app-side `TypeError` (`Cannot read properties of undefined (reading 'content')` inside the Kylas app's own minified `openCallLogForm` function) via `ErrorCollector`, correlating with a genuine failure in a *different* test at the exact moment two concurrent workers were both interacting with the Log a Call flow — same failure family, same CI conditions, not proven identical to CL32/33's exact occurrence. Full detail and evidence in `APPLICATION_BUGS.md` #1. **Code-side response**: `openLogACallForm()`'s existing 5-attempt reload-and-retry structure was correct and left unchanged (a full reload is the right mitigation for a transient client-side race); added capture-and-log of the real caught error + current URL on every retry attempt, and the final exhaustion error now surfaces the last real error instead of a bare "did not open" message — so a recurrence is immediately diagnosable instead of a mystery flake.
- **D28 (`deals.rbac.spec.ts:1174`, "restricted user can clone their own deal") — a real, previously-undetectable gap: `cloneDeal()` never verified it was actually looking at the Clone modal.** `#editEntityModal` is a shared container reused for Edit/Clone/Add-Contact/Add-Quotation on Deals; two sibling flows in the same file (`addContactToDeal()`, the Add-Quotation flow) already guard against this by checking `.modal-title`, but `cloneDeal()` never did — it just waited for the container to be visible, then polled the Name field for up to 10s waiting for "Copy" to appear, which is what actually failed in the sandbox run (`Received string: "Deal-Frozen Marble Cheese-5bvR"`, no "Copy", after 23 polls). **Fixed**: added the same `.modal-title` → "Clone Deal" check (live-confirmed this session) the sibling flows already use, so a wrong/stale modal now fails immediately with a clear cause instead of a confusing 10s-later "Name field not pre-filled" error; also widened the Name-field pre-fill timeout from 10s to 20s as a real, evidence-based safety margin (the original "8/8 clean" baseline for that wait predates this run's confirmed real `--workers=2` load). Both new `expect()`s wrapped in `withSessionExpiryRecovery()` per rule 3 (a gap locator-reviewer caught — the pre-existing Name-field check in the same method had the same gap, fixed at the same time). **Applied the identical hardening to `TasksPage.cloneTaskViaEllipsis()`** (same shared-modal architecture, and previously WEAKER than Deals' pre-fix version — it never checked the Name value at all, meaning a wrong modal there could have silently saved a clone with the unchanged original name and zero error). Both verified 3/3 clean on staging.
- **Quotations detail-page-after-create test (`quotations.rbac.spec.ts:304`) — a real, confirmed code bug: `QuotationsPage.waitForListReady()` never actually checked readiness.** It only did `waitForLoadState('domcontentloaded')` + a blind `waitForTimeout(1000)` — no check that the list or "Add Quotation" button had rendered, unlike `CallLogsPage.waitForListReady()`'s already-proven race between the list container and the header button. Combined with `openCreateForm()`'s `createButton().click()` having **no timeout at all**, if the button took longer than 1s to render under real load (this run's confirmed `--workers=2`), the click waited the rest of the 480s test for a button that either eventually rendered or never did — matching the exact failure signature (`Test timeout of 480000ms exceeded` + "browser has been closed" waiting on `locator('button').filter({hasText:'Add Quotation'})`). **Fixed**: `waitForListReady()` now races the list container against the create button (mirroring `CallLogsPage`'s proven pattern); `openCreateForm()`'s click now goes through the bounded `this.click()` helper. **Swept the same file for the already-documented known-unfixed `fillOwner()` unbounded click** (named in `.claude/reference-patterns.md` §3) and fixed it with the same bounded-click + 3-attempt-retry pattern already proven in `CompaniesPage`/`LeadsPage`'s `openUserShareTypeSearch()`. Verified 3/3 clean on staging. Other named-but-unfixed unbounded-click instances in this file (several random-option pickers) remain unfixed — a large, separately-scoped cleanup, not attempted this session.

**Task 1b — codebase-wide date-time-picker audit (done despite CL39 turning out unrelated, per explicit request to cover the class defensively):** grepped every date/time picker interaction site across all 9 modules. Found and fixed genuinely duplicated, un-fixed blind-wait anti-patterns in `CallLogsPage.selectTimeInPicker()` (4 blind waits between/after rc-time-picker column clicks) and `MeetingsPage.fillTimePicker()` (3 blind waits) — both duplicating a shape already correctly fixed with zero blind waits in `BasePage.selectDateTimeCustomField()` (the TC23 fix above). Also removed the identical redundant-blind-wait pattern from 2 calendar-navigation loops in `MeetingsPage.ts` (date fill + reschedule) and the loop-internal instance in `DealsPage.selectDateInPicker()`/`QuotationsPage.selectDateInPicker()`. **Deliberately left one wait per Deals/Quotations untouched**: a `/* Firefox: wait for calendar open animation to settle */`-labeled wait predating this session, since this project genuinely runs a local `firefox` project (not just chromium) and no live Firefox verification was possible this session — flagged as a stale, undocumented (commit `68e4e3c`, no linked repro) claim worth re-verifying live on Firefox in a future session, not removed on inference alone. Tasks/Leads/Companies/Contacts have no native date/time picker of their own (only the already-fixed shared custom-field methods) — nothing to change there. All fixes verified live via the existing test suite (BasePage's zero-wait pattern was independently re-confirmed working correctly in every verification run this session).

**A 6th, related finding surfaced by this session's own stress-testing, not one of the original 5 CI failures:** re-running the full `call-logs.rbac.spec.ts` under `--workers=2` (to gather evidence for CL32/CL33) caught a *different* test — CL18/"restricted user should update all editable fields..." — failing twice, with two different proximate symptoms each time (the app-side PAGEERROR described above once; a plain `TimeoutError` waiting for `button[data-original-title="Edit"]` to become visible the other time). **Call recording `ERR_BLOCKED_BY_ORB` — root cause corrected 2026-08-11, was NOT an application bug.** Previously documented here and in `APPLICATION_BUGS.md` #1 as a confirmed Kylas backend/signed-URL defect. ### Products & Services — confirmed mechanisms and quirks

Everything below is live-confirmed (via DOM inspection, network capture, or direct reproduction), not inferred — see `PRODUCTS_AND_SERVICES_PROGRESS.md` for the full build/investigation history behind each item.

- **CKEditor 5 description field requires calling into its internal data model directly, not the DOM.** CKEditor 5 maintains its own virtual data model separate from the rendered DOM; a plain `.fill()`/`.type()` against the contenteditable region only mutates the visible DOM, not the model that actually gets serialized into the save payload. `ProductsAndServicesPage.setDescriptionViaCkEditor()` reaches the live editor instance directly: `document.getElementById('0_22_input_description').querySelector('.ck-editor__editable').ckeditorInstance.setData(text)`.
- **Units is a genuine multi-select control, but every workflow only ever picks exactly one option from it.** Confirmed live: the control's value-container carries `is-invalid__value-container--is-multi`, selecting an option renders a real removable chip, and the saved record's `units` field is a true array (`"units":[{"id":...,"name":"Kilograms (kgs)",...}]`). Opening the menu requires `ArrowDown` after focus (react-select's async "press Down to open" pattern), not an immediate click-to-open like the single-select Country/Category controls. **This distinction caused a real, CRITICAL-tier incident**: `selectFromReactSelect()` originally had no "clear existing chip(s) first" step — harmless for single-select fields (a new pick replaces the old one automatically) but destructive for Units, where a new pick only ever *adds* a chip, and a react-select menu excludes already-selected options from its own list — meaning a second call targeting an already-selected value finds zero matching options and times out. This corrupted the permanent `adminActive` fixture (id 53242) in production data before being caught, root-caused, and fixed (bounded chip-clear-first logic, mirroring `BasePage.selectRandomFromMultiValueReactSelect()`'s already-proven shape) — see the dedicated CRITICAL INCIDENT section in `PRODUCTS_AND_SERVICES_PROGRESS.md` for the full incident report, approved fix, and verification.
- **Product name uniqueness is enforced live, inline, as-you-type/on-blur — not at save time.** `GET /products/has-duplicates?fieldName=name&value=<value>` fires on Name-field interaction and returns `{"duplicate": true|false}`; `hsnSacCode` is checked the same way. This is a genuinely different validation shape from most other modules' save-time-only server errors — `assertDuplicateNameFieldError()` asserts against this live field-level state, not a save-time toast.
- **There is no edit icon anywhere in the Products & Services UI.** Clicking a list row navigates directly to `/setup/products-services/edit/{id}` — row-click itself IS the "open for edit" action, not a separate button. (This is also why the module has no detail page at all — `edit/{id}` doubles as both the view and edit surface; see `.claude/architecture.md`'s new Products & Services deviations section for the full structural picture.)
- **Deal edit + product add triggers a real "Distribute Equally" reconciliation requirement — not an app bug, a real feature the automation must drive through.** When a Deal's Total changes after part-payments were already configured (e.g. adding a product row during edit), Kylas shows an "unallocated amount" banner (`button.distribute-unallocated-btn`) that must be resolved via a modal (`.installments-modal.distribute-modal`, rendered as a `<body>`-level portal, NOT nested inside the triggering `#editEntityModal` — confirmed live, a locator-reviewer scoping advisory to nest it was disproven by direct DOM inspection) before Save's own click handler does anything at all (confirmed via exhaustive network capture — zero requests attempted client-side until resolved). `DealsPage.handleDistributeUnallocatedAmountIfPresent()` (called from `updateDeal()`) detects and clicks through this automatically; `deals.spec.ts`'s dedicated `D41` test (renumbered from `D39` on 2026-08-11 to resolve a collision with `deals.rbac.spec.ts`'s own pre-existing `D39`) exercises and asserts the full flow explicitly. **This was initially, incorrectly concluded to be "a genuine Kylas application bug, unfixable" after exhaustive headless investigation — the user personally verified in headed mode that it was a real, working feature the automation was simply missing a step for.** Standing lesson, now a hard rule for this session's fix phase: never conclude "app bug" from headless/automated evidence alone — verify live, in headed mode, first.
- **A real, intermittent "element detached from the DOM" race on custom-field date pickers during Deal edit flows — root-caused (partially), fixed, but the exact trigger is NOT fully pinned down.** `BasePage.selectDateCustomField()`'s final day-cell click can fail with a genuine Playwright "detached from the DOM" error, observed in ~50-58% of real Deal create+edit cycles that reach this code path, always on the edit flow's FIRST calendar-driven interaction, never on create. The originally-suspected mechanism ("previous field's calendar didn't finish closing") was **directly disproven** via live `MutationObserver` instrumentation: all of a Deal's `SingleDatePicker` widgets (13-16+, one per part-payment row plus the 2 custom date fields) are permanently mounted and only CSS-hidden — they never add/remove from the DOM, so there is no "calendar closing" race to wait for. A follow-up fix (a 3-attempt reopen-and-retry loop before falling back to the pre-existing typing fallback) was verified via 12 real runs to have a **0% retry success rate** — every one of 7 real occurrences exhausted all 3 attempts; all real recovery came from the already-existing typing fallback, not the new retry logic — proving the condition is sustained across several seconds once triggered, not a momentary blip. **Simplified accordingly to 1 attempt** (cheap insurance, not because retrying is proven to ever help) before deferring to the fallback; re-verified with a second independent 12-run batch, 24/24 total across both batches. The leading (still unconfirmed) theory for the root trigger: `fillEditForm()`'s preceding rapid-fire field fills (~60-120ms apart, far faster than a real user) can leave a React re-render lagging behind, landing unpredictably right as the edit session's first calendar-driven click is in flight — plausible and consistent with all observed evidence, but not proven with a captured smoking-gun mutation burst (two live-capture attempts for that were technically unreliable). **Practical impact:** this is a shared `BasePage` method used by all 9 modules with custom fields — the warning may appear in any of their logs during an edit flow with date custom fields; this is expected, self-healing behavior (the final "date set to:" success line always follows, confirmed correct via a separate persistence check), not a regression. Two confirmed real application bugs found during this work (a `removeDimension()` client-side `TypeError` on empty-row removal, and a non-functional "Report Name" list-sort control) are documented in `APPLICATION_BUGS.md` entries #2/#3, not here.

- **A third-party-widget-triggered react-select race is a repo-wide risk, not Reports-specific — confirmed live, fixed, and the fix pattern is now documented for reuse.** The `viasocket.com` chatbot widget embedded on every page of this app can fire an async DOM mutation 20–160ms after a react-select menu opens, closing it again before an automated click lands — because the widget loads on every page, **any** react-select interaction anywhere in this codebase is theoretically exposed, not just the one it was found on in Reports. Two unsafe/insufficient approaches were tried and ruled out first: blocking the widget's domain via `page.route().abort()` caused it to retry aggressively and hung the entire browser session for 30 minutes (a new, distinct gotcha from the already-documented `route.fetch()`-based session-recovery issue above — this one is about blocking a third-party domain outright, not replaying a request); waiting for the widget's own network response before interacting was insufficient, since the disruptive re-render lands 130–160ms *after* the response, not synchronously with it. The proven fix — open, wait for visible, then confirm the menu **survives a stability window** before trusting it (a `waitFor({state:'hidden'})` that times out is the success case) — is documented as a reusable pattern in `.claude/reference-patterns.md` §18. Verified via 45 combined live trials with zero failures. If any other module's react-select interaction shows an intermittent "menu closed before I could click the option" symptom, check for this exact race before assuming a module-specific bug.

Call Log's own real equivalent is **"Logged At"** (its confirmed option list: `Logged At`, `Start Time`, `Date`, `Updated At`, `Date Time Picker`) — a call log's canonical timestamp is when it was logged, the same moment as its creation, so "Logged At" is the correct field to filter/compare against for any Call-Log-scoped date-window check. Don't assume any date-filter/date-field option list is identical across entity types without confirming live for the specific one being used.
- **Playwright's `dependencies` project feature is confirmed unsafe for this repo's real CI shape — do not re-attempt it for any future "run this after everything else" ordering need.** Investigated via a real, disposable scratch Playwright project (not assumed from documentation): a project selected via `--project=X` that depends on another project via `dependencies: [...]` **silently bypasses `--grep` filtering for the dependency**, even when that dependency is also separately, explicitly co-selected on the same command line. Concretely for this repo: adding a `dependencies: ['chromium']` project and updating `dev.yml`/`qa.yml`'s existing `--project=chromium --grep @smoke|@regression` invocations to also select the new project would silently balloon `chromium` to run its *entire* untagged test set on every single run, undetected, since Playwright doesn't error or warn about this — it's silent scope expansion baked into the mechanism itself. The only way to avoid this is to invoke the two projects in **separate** `npx playwright test` commands — which instead re-runs the entire dependency project's suite a second time in full (confirmed no cross-invocation deduplication), doubling that branch's CI runtime. Both consequences were independently confirmed live via `--list` counts, not inferred. **If a future module needs "verify against everything the rest of the suite created," don't reach for `dependencies` — see the next bullet for what was chosen instead.**
- **Run-count/aggregate verification design decision: self-contained per-test windows, not a whole-suite-spanning check — and why `globalTeardown` was investigated and rejected as the way to do the latter.** Reports' run-count verification (16 tests, one per entity type × admin/restricted) creates its own small batch of records per test and verifies only against that batch, deliberately **not** attempting to verify against everything the rest of a CI run's suite created. `globalTeardown` was investigated as a way to achieve the original, more ambitious whole-suite design (confirmed live: it does run exactly once, after every test across every worker finishes, even if other tests failed, and cross-worker timestamp coordination via shared local files works reliably for this repo's real CI, which never uses `--shard`) — but rejected for two confirmed, concrete reasons, not just extra complexity: (1) **a `globalTeardown` failure is invisible to this repo's own notification email** — Playwright reports it as a separate top-level `errors` entry, distinct from any test's pass/fail, and this repo's `ReportParser.ts`/`NotificationService.ts`/`EmailTemplate.ts` never read that field, confirmed via direct grep; a teardown-based check failing today would produce an email that still says everything passed. (2) `globalTeardown` gets no `Page`, no fixtures, no session-expiry recovery, no `ErrorCollector` — matching the current design's UI-level drill-through depth (build a real report, switch chart type, click into a bucket, verify the real destination list) would mean hand-launching a browser outside the test framework with none of its safety nets, or accepting a real reduction to an API-only check. **A prior, independent attempt at whole-suite verification (found on a separate, unmerged, dangling branch, `feature/reports-module-20260817`) took a materially more ambitious approach — a global creation ledger tracking every entity-creation call site, cross-checked against a baseline snapshot — and is a genuinely better starting shape than a naive teardown-based window if this is ever revisited**, but that branch's own implementation had two confirmed real bugs of its own: the identical `dependencies`/grep-bypass flaw above, and an incomplete ledger (only 2 of the many real Lead-creating call sites across the codebase were ever instrumented, guaranteeing an undercount the moment other modules' tests ran alongside it). If whole-suite-scale verification is ever revisited, start from that ledger-plus-baseline idea rather than re-deriving it, but budget for completing the ledger across every entity-creating call site in the codebase and fixing the CI-invocation problem properly — neither was solved in that attempt.

### Notification/reporting pipeline — investigation findings (2026-08-24)

Full investigation and redesign work: branch `feature/notification-system-redesign-20260823` (uncommitted as of this writing).

**Playwright's raw JSON report carries `results[].errors[]` (plural — every error encountered during an attempt, in order) as a field distinct from `results[].error` (singular — always just `errors[0]`), and the plural array can hold a strictly more useful, specific message the singular field never surfaces.** `ReportParser.ts` only ever read the singular `error` field before this investigation. Confirmed live on a real historical flaky test (a Quotations detail-verify test, prod report 2026-07-31): `error.message` was the generic `"Test timeout of 480000ms exceeded."`, while `errors[1].message` was the actual, specific, actionable cause — `"Wrong quotation loaded — page title... does not contain quotation number..."` — thrown by application code moments before the outer timeout gave up. Any future code reading Playwright's raw JSON report for diagnostics should read the full `errors[]` array (the LAST entry is most proximate to when the test actually gave up), not just the singular `error` field, which can hide the real cause behind a generic timeout message.

**A task briefing can describe a feature/section that was never actually built in the code under investigation — confirmed real, not a one-off.** A redesign brief for this codebase's notification email referenced a "Reports Verified" section; investigating found it doesn't exist anywhere in `EmailTemplate.ts` (confirmed via grep, zero matches) — most plausibly a conflation with the unrelated Reports UI module's own drill-through test coverage, or a memory of an abandoned, never-merged branch's in-progress design. **Notification pipeline's own enrichment-layer convention, worth reusing for any future addition to the reporting pipeline:** `FailureDetailBuilder.ts` establishes the pattern for adding a new derived/enriched view over already-classified pipeline data — keep raw fs/parsing access isolated in its own small loader module (e.g. `KnownIssuesIndex.loadKnownIssuesIndex()`), keep the actual enrichment/derivation logic pure (no fs/network calls inside it, testable by passing in already-loaded data via a plain context object), and let the caller (`NotificationService`) own wiring the loader's output into the enrichment function's input. Mirrors the same pure-logic-first convention already established by `RunHistory.ts`/`AutomationHealth.ts`/`FailureAnalyzer.ts` — don't reach for `fs`/`child_process` calls inside a new analysis function; add a dedicated loader instead.

### CI reporting-history ledger — root cause confirmed, fixed and merged to dev (2026-08-24/25)

**`ci/reporting-history` (the branch `RunHistory.ts`/`syncHistory.ts` write run-history to, feeding Module Analytics' trend column and recurring-flaky/regression detection) had never received data in any real CI run, on any branch, ever** — masked by its own deliberate "never fail the build" try/catch around the push step. **Confirmed real root cause (found only on a third investigation round, after two earlier rounds chased the wrong mechanism):** `syncHistory.ts` clones into its own fresh temp directory to do its git work, and `actions/checkout@v5`'s `token: secrets.PIPELINE_TOKEN` only authenticates the *original* checked-out workspace (a local-scoped git config entry) — it was never passed through to that temp clone, and nothing in `syncHistory.ts` read/injected it either. Every `git push` was therefore a fully anonymous request against a public repo, doomed to fail with 100% consistency regardless of timing or retry budget. **A second, compounding bug hid this for over a month:** the push-failure handler had no real error classification at all — it unconditionally logged "rejected (concurrent update)" on any non-zero `git push` exit without ever reading the actual captured git stderr, so every CI log asserted a plausible-sounding but false cause.

**Two earlier fix rounds (2026-08-24/25) chased that false "concurrent update" signal and were both superseded, not because they were sloppy but because the log they trusted was never checked against the real git error text — kept here as one line for that lesson, not for their own detail:** round 1 added a small fixed-delay retry (300/800/1500ms) for a fetch-after-rejection race; round 2 replaced it with an elapsed-time-bounded exponential backoff (45s ceiling) after round 1's budget proved insufficient in real CI. Both were real, correctly-engineered fixes for a race condition that was never actually the cause — `git ls-remote origin ci/reporting-history` returned empty throughout both rounds, proving nothing had ever even won the "race" they were tuning for.

**Real fix (`fix/history-sync-race-condition-20260824`, since merged to `dev` via commit `4477e0f`):**
- **Authentication:** a new `gitAuthEnv()` injects the identical Basic-auth header `actions/checkout` itself uses, via `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` env vars passed through the file's own `sh()`/`shSafe()` git-invocation helpers — chosen over URL-embedding (would print the token into CI logs on any failing command) or `git config --local` (relies on a call site remembering to run it, writes the secret to disk).
- **Structural secret-leak prevention:** all logging now routes through `log()`/`warn()`, which unconditionally scrub the registered `PIPELINE_TOKEN` from any string before it reaches an output sink — defense-in-depth on top of the auth mechanism, not a substitute for it.
- **Real, extensible failure classification** (`classifyGitFailure()`), replacing the old unconditional "assume concurrent update" guess: an ordered list of named classifiers (auth failure, non-fast-forward, missing-remote-ref) checked against the real captured git error text, falling through to an honest `unclassified` (never retried) when nothing matches — so the next unrecognized git failure gets a true label instead of being silently folded into the wrong bucket.
- Also fixed in the same pass: `dev.yml` and `staging-promotion-gate.yml`'s `test-staging` job were missing from the original 5-workflow permissions fix — all 7 workflows invoking `history:sync` now have `permissions: contents: write` + a credentialed checkout token.

**Verified:** auth-header transmission confirmed byte-for-byte against a real local HTTP server; the real `git` auth-failure error text (`fatal: could not read Username for '<url>': No such device or address`) captured live and used to ground the classifier pattern, not paraphrased; classifier + redaction logic 12/12 checks passed (auth/non-fast-forward/missing-ref/novel-unclassified text, secret-scrubbing including inside a thrown `Error`'s own `.message`/`.stack`); the original concurrent-race reproduction (two `syncHistory.ts` processes against a shared local bare repo) re-run 3/3 clean with the new code, confirming no regression to the one case the old "concurrent update" guess was actually right about. **What could not be verified locally:** a real push succeeding against actual github.com with the real token — this repo's git safety rules prohibit any push from this session; that last mile is confirmed only by a real CI run.

**Standing lesson:** a log message is not evidence. This bug survived two genuinely careful fix rounds because both trusted an unverified log line instead of reading the real git error text it claimed to summarize.
