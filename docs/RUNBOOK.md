# CI Failure Runbook

> **Purpose:** Symptom → likely cause → first check → where it is documented, for failures seen in this repo's CI and local runs.
> **Read when:** A CI run or local run failed and you need to know whether it is a code bug, an app bug, an environment effect or a pipeline problem.
> **Size budget:** 40k chars (hard cap 60k)
> **Last verified:** 2026-10-28 @ 566df8c

Every row comes from a real incident. "Documented" links point at the resolved-history topic file; open items are in [KNOWN_ISSUES_ACTIVE.md](./KNOWN_ISSUES_ACTIVE.md). Check that first: your failure may already be a tracked open item.

## First five minutes

1. **Get the raw log, not the web viewer.** `gh run view <run-id> --log > run.log`. The Actions web viewer can appear frozen on a long, high-volume run while the raw log keeps writing.
2. **Find the first failing test, not the retry's error.** In a failing test's output the attempt-1 error is the cause; the retry error is often a downstream symptom. In the JSON report `results[].errors[]` (plural) can hold a more useful message than the singular `error`.
3. **Check `misc-errors.json`** (`reports/<env>/misc-errors.json`, per-shard artifact `misc-errors-<env>-<shard>`): unexpected 4xx/5xx, `pageerror`, and the app's own JS errors near the failure time. It is overwritten by every later run in the same environment; copy it first.
4. **Open the trace** (`test-results` artifact, `trace.zip`) or the failure screenshot. Several classes below are only identifiable from the screenshot (the 429 page, the error-boundary page).
5. **Classify before fixing.** Application bug vs code bug, per the `failure-triage-investigator` convention ([agent guide](../.claude/AGENT_DELEGATION_GUIDE.md)). Never conclude "app bug" from headless evidence alone; verify live and headed. Never call a flake fixed from one passing run: re-run 3-5 times in isolation. A flake that vanishes in isolation can still be real under CI concurrency.
6. A message in a log is not evidence. Read the real error text (git stderr, HTTP body) it claims to summarize.

## Local-run problems

| Symptom | Fix / check |
|---|---|
| `Missing required environment variable: X` | The active `ENV`'s variables are incomplete in `.env` (see [README](../README.md#quick-start)) |
| Auth errors mid-run on QA | `rm -rf src/auth/storageStates/qa/` forces a fresh login |
| `ts-node` script fails `TS2591` while `tsc --noEmit` passes | `tsconfig.json`'s `"types": ["node"]` was reverted; `--transpile-only` hides this class |
| `npm run test:<m> -- <args>` ignores your flags | Args attach to the last `&&` command (`npm run notify`). Use `npx playwright test <paths> <flags>` |
| Clone lead/contact form rejects save | Change email/phone: clone pre-fills the originals |
| `saveQuickTask()` hangs from an entity detail panel | Use `saveQuickTaskFromEntityDetail()` |
| Docs numbers look stale | `npm run docs:refresh`, then `npm run check:docs` |

## Jenkins sharded runs: setup and operation

Design: [ADR 0012](./adr/0012-jenkins-sharded-runs-locks-and-guard.md); behaviour: [CI_PIPELINES.md](./CI_PIPELINES.md) section 5.1. Nothing here has been exercised by a real sharded build yet ([KI-47](./KNOWN_ISSUES_ACTIVE.md)). Do the steps in this order; each says whether it can be undone.

Done on this host on 2026-10-28 (by the maintainer; Claude did not run it or re-check it). **With sleep disabled the laptop must stay plugged in:** a closed laptop keeps running and heats up. | Reversible: `sudo systemctl unmask sleep.target suspend.target hibernate.target hybrid-sleep.target` |

| 6 | **Test from a feature branch against QA.** Widen the multibranch job's branch filter (job `kylas-automation`, Configure, Branch Sources, Filter by name with regular expression) from `^(dev\|qa\|stage\|prod\|main\|sandbox)$` to include the branch, for example `^(dev\|qa\|stage\|prod\|main\|sandbox\|feature/jenkins-main-sharding-20261028)$`, scan, then Build with Parameters (the parameters appear after the first build of the new file). A feature branch resolves to QA. The unsharded path has **no scope option** (`TEST_GREP` and `FF_ENTITIES` are ignored without `SHARDED_TEST`): it runs the full suite, estimated 8.6-11 h for the current suite (ADR 0012, unmeasured; the only full unsharded Jenkins run, `main` #8, took 316 min on a much smaller suite). Only QA is allowed on this path. Automatic builds of that branch only check out. | Reversible: restore the original expression afterwards |
| 7 | **In-process script approval.** After the first run, Manage Jenkins, In-process Script Approval: approve only signatures the build lists as pending. Which ones, if any, is unknown until a run. | Approved entries are listed on the same page; confirm in the UI how to revoke |
| 8 | **Executors.** The Built-In Node has 6. A sharded build holds 1 executor for the whole build (including the approval wait) plus the lanes of the running track: 3 at the default 2 lanes. Other builds parked at an approval hold one each. 6 is enough at 2 lanes; raise it (Manage Jenkins, Nodes, Built-In Node, Configure, Number of executors) only when running 3-4 lanes while other builds are parked, and mind memory: each lane is 2 workers ([ADR 0012](./adr/0012-jenkins-sharded-runs-locks-and-guard.md)). | Reversible |
| 9 | **Go live.** Set `KYLAS_SHARDED_BRANCHES` (step 4) only after a full sharded QA run (the `qa` branch's `@regression` selection) has been compared with GitHub's `qa.yml` results for the same tests; an unsharded 9-11 h Jenkins baseline is optional, not required. Then restore the branch filter (step 6). | Reversible: unset it, or `KYLAS_SHARDING=off` (sharding only, see the warning below) |

**`KYLAS_SHARDING=off` only turns sharding off.** The account locks and the collision guard stay active on every Jenkins run, and `sandbox` stays on staging. If the `github-credentials` PAT expires or loses Actions read, the fail-closed guard refuses every Jenkins run and the kill switch does not help: renew the `github-credentials` token (step 3 checks it).

**When a lock is held.** A second build waits at `Taking lock '<name>'` until the holder finishes; Manage Jenkins, Lockable Resources shows who holds it. The lock is released on abort.

**Before dispatching `main.yml` or `prod.yml` by hand,** check that no Jenkins build is running against the same account (the Jenkins guard sees GitHub; GitHub cannot see Jenkins, [KI-46](./KNOWN_ISSUES_ACTIVE.md)).

## When it is an app bug

Confirmed real Kylas bugs are kept in a file outside this repo (not tracked), not in the engineering docs. A test stays red for a real app bug; do not mask it. Add a new confirmed one there with live evidence.
